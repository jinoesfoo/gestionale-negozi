Chiudi il compito corrente. Rispondi all'utente in italiano.

1. Esegui `bash .claude/hooks/mostra-stato.sh` (sola lettura). Se la fase non è `chiusura`, fermati e spiega che prima serve `APPROVO` dopo la revisione. Poi verifica di essere sul ramo del compito (nome in minuscolo, es. `fon-t01`), non su `main`: se sei su `main`, crea il ramo con `git switch --no-track -c <ramo>` prima di qualunque commit, perché già il passo 3 può farne uno.
2. **Una pull request di compito alla volta.** Esegui `gh pr list --state open --json number,title,headRefName`. Contano solo i rami che hanno il nome di un compito (`^[a-z]{3}-t[0-9]{2}[ab]?$`) diverso da quello corrente: le pull request delle dipendenze e i rami di prova (`prova-*`) non contano. Se ce n'è una, fermati: l'utente la unisce o la chiude, poi rilancia `/chiudi-compito`. Così GitHub, al momento dell'unione, di norma non trova due compiti in conflitto (il controllo si ripete al passo 9, subito prima di aprire la pull request). Se c'è già una pull request aperta di questo compito (per esempio dopo `TORNA AL CODICE` per la CI rossa), vai avanti: al passo 9 basta spingere. Se invece la sua pull request è già unita (una correzione dopo l'unione), al passo 9 ne apri una nuova.
3. **Allineamento a main.** Se c'è un'unione con main già avviata (esiste `.git/MERGE_HEAD`, per esempio dopo `TORNA AL CODICE` per un conflitto), controlla con `git diff --name-only --diff-filter=U` che non restino conflitti e concludila con `git commit --no-edit`. Poi esegui `git fetch origin`. Se `origin/main` è andato avanti rispetto alla base del ramo (`git merge-base HEAD origin/main` diverso da `git rev-parse origin/main`):
   - prima, se ci sono modifiche non salvate, un commit di tutto il lavoro (`git add -A`, `git commit`); poi, in ogni caso, `git merge --no-edit origin/main`. Niente stash, perché un conflitto in un test lascerebbe le modifiche nello stash, fuori dall'impronta dei test, e niente rebase, che richiederebbe una spinta forzata, non permessa: l'unione su GitHub è «Squash and merge», quindi i commit del ramo e quello di unione non restano nella storia.
   Se l'hook risponde che `origin/main` cambia i file del metodo, fermati: quel comando lo esegue l'utente nel suo terminale (la sandbox non lascia scrivere quei file a Claude); poi riprendi da qui.
   Se compaiono conflitti:
   - solo in `specs/` o `docs/` (per esempio due caselle vicine spuntate dalle due postazioni): risolvili tenendo le modifiche di entrambe le parti, poi `git add` e concludi l'unione con `git commit --no-edit`;
   - in qualunque altro file: fermati, non toccare i file e spiega quali sono in conflitto. L'utente scrive `TORNA AL CODICE`: l'unione resta avviata, e Claude la conclude in fase codice con `git commit --no-edit` dopo aver risolto (se fosse ancora aperta, la conclude il passo 3 alla chiusura successiva). Se il conflitto è in un test o nella configurazione dei controlli, dopo `TORNA AL CODICE` l'utente scrive anche `TORNA AI TEST`: il conflitto si risolve in fase test, poi `APPROVO`, e l'unione si conclude in fase codice. Poi servono di nuovo revisione e chiusura.
   Se dopo l'unione l'hook dice, al commit o alla spinta, che un test o la configurazione dei controlli sono cambiati, perché li avevano cambiati tutte e due le parti, l'utente scrive `TORNA AL CODICE`, poi `TORNA AI TEST` e poi `APPROVO`, senza rimettere il file com'era.
   Dopo l'allineamento, se sono cambiati `package.json` o `pnpm-lock.yaml`, esegui `pnpm install`.
4. Esegui, nell'ordine, e riporta l'esito reale di ciascuno: `pnpm lint`, `pnpm typecheck`, `pnpm test`, e nella gabbia `bash .claude/hooks/gabbia.sh test:int` (se il compito tocca database, permessi o lavori in background) e `bash .claude/hooks/gabbia.sh test:e2e` (se il compito tocca pagine o flussi). Questi due comandi girano fuori dalla sandbox: scrivili da soli, ciascuno nella sua riga. Dopo l'allineamento i controlli girano sul codice che verrà davvero unito. Se `package.json` non esiste ancora (compiti di yoo chiusi prima che FON-T01 sia su main), questi controlli non esistono: dillo e scrivilo nella pull request. Se un controllo fallisce, fermati: spiega cosa non va e indica all'utente di scrivere `TORNA AL CODICE` (codice da correggere) oppure, dopo `TORNA AL CODICE`, `TORNA AI TEST` se serve modificare i test.
5. Nella specifica del compito:
   - spunta la casella del compito (`- [ ]` → `- [x]`), e solo quella;
   - annota gli esiti dei punti [VERIFICA] del compito, se presenti;
   - annota ogni deviazione dalla specifica decisa durante il lavoro.
6. Prima del commit controlla di nuovo di essere sul ramo del compito, non su `main` (passo 1).
7. Fai il commit con messaggio `<ID>: <titolo breve del compito>` e, nel corpo, l'elenco dei requisiti coperti. Il commit comprende anche il registro di questa postazione, `registro/compiti-<postazione>.log`. L'hook rifiuta un commit che porta modifiche ai file del metodo, al registro dell'altra postazione, caselle di altri compiti o test cambiati dopo la fase test. Se non resta niente da salvare, perché il lavoro e la casella sono già in un commit (per esempio nella chiusura dopo `TORNA AL CODICE`), vai al passo 8.
8. Se dopo il commit `origin/main` è andato avanti di nuovo, ripeti il passo 3 e il passo 4.
9. Spingi il ramo con `git push origin <ramo>` (senza `-u`: scriverebbe nella configurazione di git, che la sandbox protegge). Se non c'è una pull request aperta di questo ramo, rifai subito il controllo del passo 2 (se intanto l'altra postazione ne ha aperta una, fermati come lì), poi aprila con `gh pr create --base main --head <ramo>`: titolo `<ID>: <titolo breve del compito>`, come il commit del passo 7; descrizione con postazione, requisiti coperti, test aggiunti, esito dei comandi, eventuali nuove variabili d'ambiente e valori di sviluppo cambiati negli esempi: le variabili sui server **prima** dell'unione, e le une e gli altri nei file di ambiente locali dell'altra postazione (per esempio `.env.test`) quando l'utente unisce (li scrive l'utente, aggiornando solo quelle righe; dopo FON-T08 ogni unione su `main` arriva sul server di test).
10. Chiudi con, in grassetto: **"Controlla la pull request; quando la CI è verde uniscila con «Squash and merge», poi scrivi CHIUSO: l'hook lo accetta solo quando il compito è su main."** Se il compito ha prove da fare sui server dopo l'unione, o una parte in produzione (`docs/due-postazioni.md`, «Il server di test condiviso»), aggiungi quali sono e in che ordine: togliere il fermo dei rilasci se l'ha attivato questo compito e rilanciare il rilascio di `main` con l'avvio a mano (un'unione fatta con il fermo attivo non è stata rilasciata), aspettare il tag `tested-` di `main`, far creare all'utente il rilascio `v*`, fare le prove, scriverne l'esito; solo dopo `CHIUSO`. Se la pull request aggiunge variabili d'ambiente o cambia valori di sviluppo negli esempi, ricorda all'utente di aggiornare quelle righe anche nei file di ambiente locali dell'altra postazione quando unisce, senza ricopiare i file. Se una prova dopo l'unione usa un segreto di prova di GitHub (FON-T08, `KNOWN_HOSTS`), ricorda all'utente di crearlo prima dell'avvio a mano, con il nome usato dal flusso del ramo.
