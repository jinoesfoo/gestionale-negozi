Chiudi il compito corrente. Rispondi all'utente in italiano.

1. Esegui `bash .claude/hooks/mostra-stato.sh` (sola lettura). Se la fase non è `chiusura`, fermati e spiega che prima serve `APPROVO` dopo la revisione.
2. **Una pull request di compito alla volta.** Esegui `gh pr list --state open --json number,title,headRefName`. Contano solo i rami che hanno il nome di un compito (`^[a-z]{3}-t[0-9]{2}[ab]?$`) diverso da quello corrente: le pull request delle dipendenze e i rami di prova (`prova-*`) non contano. Se ce n'è una, fermati: l'utente la unisce o la chiude, poi rilancia `/chiudi-compito`. Così GitHub, al momento dell'unione, non trova mai due compiti in conflitto. Se c'è già una pull request aperta di questo compito (per esempio dopo `TORNA AL CODICE` per la CI rossa), vai avanti: al passo 9 basta spingere. Se invece la sua pull request è già unita (una correzione dopo l'unione), al passo 9 ne apri una nuova.
3. **Allineamento a main.** Se c'è un'unione con main già avviata (esiste `.git/MERGE_HEAD`, per esempio dopo `TORNA AL CODICE` per un conflitto), controlla con `git diff --name-only --diff-filter=U` che non restino conflitti e concludila con `git commit --no-edit`. Poi esegui `git fetch origin`. Se `origin/main` è andato avanti rispetto alla base del ramo (`git merge-base HEAD origin/main` diverso da `git rev-parse origin/main`):
   - se ci sono modifiche non salvate oltre al registro, prima `git stash push -u -- . ':(exclude)registro'` (e alla fine `git stash pop`): il registro resta sempre fuori dallo stash, perché gli hook lo confrontano con la loro copia e `main` non lo cambia mai;
   - se il ramo non ha ancora commit propri: `git merge --ff-only origin/main`;
   - se il ramo ha già commit propri: `git merge --no-edit origin/main` (niente rebase: richiederebbe una spinta forzata, che non è permessa; l'unione su GitHub è «Squash and merge», quindi il commit di unione non resta nella storia).
   Se l'hook risponde che `origin/main` cambia i file del metodo, fermati: quel comando lo esegue l'utente nel suo terminale (la sandbox non lascia scrivere quei file a Claude); poi riprendi da qui.
   Se compaiono conflitti:
   - solo in `specs/` o `docs/` (per esempio due caselle vicine spuntate dalle due postazioni): risolvili tenendo le modifiche di entrambe le parti, poi `git add` e, se il conflitto è venuto da `git stash pop`, `git stash drop`; se è venuto da `git merge`, concludi con `git commit --no-edit`;
   - in qualunque altro file: fermati, non toccare i file e spiega quali sono in conflitto. L'utente scrive `TORNA AL CODICE`: il conflitto si risolve in fase codice (l'unione resta avviata e la conclude questo passo, alla chiusura successiva), poi servono di nuovo revisione e chiusura.
   Dopo l'allineamento, se sono cambiati `package.json` o `pnpm-lock.yaml`, esegui `pnpm install`.
4. Esegui, nell'ordine, e riporta l'esito reale di ciascuno: `pnpm lint`, `pnpm typecheck`, `pnpm test`, e nella gabbia `bash .claude/hooks/gabbia.sh test:int` (se il compito tocca database, permessi o lavori in background) e `bash .claude/hooks/gabbia.sh test:e2e` (se il compito tocca pagine o flussi). Questi due comandi girano fuori dalla sandbox: scrivili da soli, ciascuno nella sua riga. Dopo l'allineamento i controlli girano sul codice che verrà davvero unito. Se `package.json` non esiste ancora (compiti di yoo chiusi prima che FON-T01 sia su main), questi controlli non esistono: dillo e scrivilo nella pull request. Se un controllo fallisce, fermati: spiega cosa non va e indica all'utente di scrivere `TORNA AL CODICE` (codice da correggere) oppure, dopo `TORNA AL CODICE`, `TORNA AI TEST` se serve modificare i test.
5. Nella specifica del compito:
   - spunta la casella del compito (`- [ ]` → `- [x]`), e solo quella;
   - annota gli esiti dei punti [VERIFICA] del compito, se presenti;
   - annota ogni deviazione dalla specifica decisa durante il lavoro.
6. Verifica di essere sul ramo del compito (nome in minuscolo, es. `fon-t01`), non su `main`. Se sei su `main`, crea il ramo prima del commit (`git switch --no-track -c <ramo>`).
7. Fai il commit con messaggio `<ID>: <titolo breve del compito>` e, nel corpo, l'elenco dei requisiti coperti. Il commit comprende anche il registro di questa postazione, `registro/compiti-<postazione>.log`. L'hook rifiuta un commit che porta modifiche ai file del metodo, al registro dell'altra postazione, caselle di altri compiti o test cambiati dopo la fase test.
8. Se dopo il commit `origin/main` è andato avanti di nuovo, ripeti il passo 3 (con `git merge --no-edit origin/main`) e il passo 4.
9. Spingi il ramo con `git push origin <ramo>` (senza `-u`: scriverebbe nella configurazione di git, che la sandbox protegge). Se non c'è una pull request aperta di questo ramo, aprila con `gh pr create --base main --head <ramo>`: titolo uguale al commit; descrizione con postazione, requisiti coperti, test aggiunti, esito dei comandi ed eventuali nuove variabili d'ambiente da aggiungere sui server **prima** dell'unione (le scrive l'utente; dopo FON-T08 ogni unione su `main` arriva sul server di test).
10. Chiudi con, in grassetto: **"Controlla la pull request; quando la CI è verde uniscila con «Squash and merge», poi scrivi CHIUSO: l'hook lo accetta solo quando il compito è su main."** Se il compito ha prove da fare sui server dopo l'unione, o una parte in produzione (`docs/due-postazioni.md`, «Il server di test condiviso»), aggiungi quali sono e in che ordine: togliere il fermo dei rilasci se l'ha attivato questo compito e rilanciare il rilascio di `main` con l'avvio a mano (un'unione fatta con il fermo attivo non è stata rilasciata), aspettare il tag `tested-` di `main`, far creare all'utente il rilascio `v*`, fare le prove, scriverne l'esito; solo dopo `CHIUSO`.
